パターン N: 複数フォーム × 片方 autocomplete 属性欠落

パターン M の補強版。片方の form が autocomplete 属性を持たない場合、自動入力側の username 複数候補チェック (rule1) が機能せず、先頭 form の自動入力ダイアログが発火してしまうかを検証する。

設計 (Confluence: フォーム判定 > PW 欄) では「同じページに複数のログインフォームがある」は保存・自動入力とも対応対象外 (×) のはずである。

会員ログイン (autocomplete 属性あり)

管理者ログイン (autocomplete 属性なし)

期待される動作: 保存・自動入力とも発火しない。ただし現行実装では 保存は押した form が拾われる (パターン M と同じ穴) 、自動入力は rule1 で先頭 form の memberId が唯一命中となり、先頭 form が対象になる恐れがある (バグ)。

実装メモ 
findUsernameInput() rule1:
  const rule1 = visibleInputs.filter(i => autocompleteTokens(i).includes('username'));
  if (rule1.length === 1) return rule1[0];
  if (rule1.length >= 2) return null;

→ パターン M では 2 個ヒット → null で自動入力遮断
→ パターン N では 1 個のみヒット → 先頭 form の memberId 採用 → 自動入力発火の恐れ

設計 (Confluence フォーム判定 > PW 欄) 除外条件:
  - 複数のパスワード欄があるフォーム
  - 用途を一意に特定できない
