SPA 形式送信テスト

React や Vue 等のフレームワークが採用しがちな 4 種類の送信パターンです。各パターンを個別のページから試してください。

各パターンを独立ページに分離しているのは、同一ページに autocomplete="username" 属性の input が複数並ぶと、ブラウザの自動入力機能が「候補が曖昧」と判定してスキップするため。1 パターン 1 ページ構成で本来の挙動を検証する。

パターン D: fetch + URL 書き換え →

fetch で送信して history.pushState で URL を書き換えるだけの純粋 SPA 形式。<form> タグ無し。

パターン E: location.assign →

location.assign による古典的な画面遷移。<form> タグ無し。

パターン F: フォーム + JS 完全制御 →

<form> はあるが送信ボタンは type="button"。submit イベントを一切発火させず JavaScript のみで処理。

パターン G: フォーム + submit 横取り →

<form> ＋ type="submit"。submit イベントを addEventListener で拾って preventDefault。React 等で典型的な書き方。

実装詳細（開発者向け） 
パターン D: fetch + history.pushState（form 無し、純粋 SPA）
  - submit イベント発火しない
  - WKNavigationDelegate 無音（pushState は経由しない）
  - テスト対象ブラウザの保存機能では検知不可

パターン E: location.assign（form 無し、ハード遷移）
  - submit イベント発火しない
  - WKNavigationType=other で WKNavigationDelegate 発火
  - JS submit listener / WKNavigationType フィルタの両方とも検知不可

パターン F: form + 完全 JS 制御（type=button、native submit せず）
  - submit イベント発火しない
  - WKNavigationDelegate も無音（native submit が起きないため）
  - テスト対象ブラウザの保存機能では検知不可

パターン G: form + type=submit + addEventListener で preventDefault（React 典型形）
  - submit イベント発火する
  - WKNavigationDelegate は無音（preventDefault で native navigation 抑止）
  - JS submit listener 方式なら検知可能 ← テスト対象ブラウザの新フローの強み

パターン G が JS injection 経由で保存ダイアログを出せれば、主要ブラウザ相当の網羅率を達成。
