モーダル / ダイアログ型ログインテスト

ページ遷移を伴わず、モーダルウィンドウ内でログインフォームが出現するパターンです。EC サイトのカート内ログインや「ログインしてください」オーバーレイでよく見る形式。

パターン J: HTML5 <dialog> + ネイティブ form 送信

HTML5 標準の <dialog> 要素 + ネイティブ form 送信。送信後は success.html へ遷移するので、WKNavigationType.formSubmitted が発火します。

パターン K: div オーバーレイ + fetch (画面遷移無し)

ログイン (パターン K)

典型的な div オーバーレイ + JS 完全制御 (form 要素なし)。送信ボタン押下 → fetch → モーダル閉じるだけで先へ進むタイプ。navigation も submit イベントも発火しないため、両方式で検知不可。

パターン L: div オーバーレイ + form + preventDefault (React 典型)

ログイン (パターン L)

React 等でよくある、モーダル内 form + submit イベント横取り + fetch。submit イベントが発火するため、JS submit listener 方式なら検知可能。

実装詳細（開発者向け） 
パターン J: <dialog> + ネイティブ form 送信
  - submit イベント発火する
  - WKNavigationType.formSubmitted で success.html に遷移
  - 検出可能: モーダル内でも form があれば通常の検出フローに乗る
  - 注意: readLoginForm.js は body 直下スキャン (querySelectorAll)。
    dialog 内の input も querySelectorAll では拾えるはず

パターン K: div オーバーレイ + JS 完全制御
  - submit イベント発火しない (form 要素なし)
  - navigation 発火しない (モーダル閉じるだけ)
  - 検出不可: 保存契機が一切ない

パターン L: div オーバーレイ + form + preventDefault
  - submit イベント発火する
  - navigation 発火しない (preventDefault + fetch)
  - JS submit listener 方式なら検出可能 ← PR #247 の新方式の強み
  - 逆に navigation policy 方式では取りこぼされる

要点:
  - モーダル内フォームの検出可否は「form 要素の有無」と「submit イベントの発火」に依存
  - form が無い型 (パターン K) は保存契機自体が存在しないため、
    どのブラウザでも保存不可 (ユーザーが手動でキーチェーンに保存する必要)
